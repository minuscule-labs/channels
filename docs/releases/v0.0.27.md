# MinuChannels v0.0.27

Compared with **v0.0.26**, this release unifies recipient selection and Send-triggered agent activation in main conversations and threads. Reusable Conversation presets remain separate.

## Select once, keep talking

Choose a participant in the composer, mention them intentionally, or use **Reply** on their message. Follow-ups keep addressing that participant until you switch. The composer shows the effective recipients that will be submitted for the next Send.

Selections belong to each person, separately for each Workspace and conversation/thread. They survive reloads in the same browser, without cross-device or live cross-tab synchronization. Incoming messages and generated agent replies cannot redirect your selection. Code, quotations and escaped mentions do not count as recipient commands.

Broadcasts and multiple explicit recipients apply only to that message and preserve the earlier sticky selection. An explicit no-recipient selection is retained; ambiguous messages do not guess an agent.

## Send starts the selected agent when needed

Being a participant makes an agent available; it does not start a session. Creating conversations, opening or restoring threads, and drafting start nobody. An addressed Send starts eligible never-bound agents and delivers the saved question, even when switching to another agent on a later message. Multiple explicitly addressed eligible agents can start together.

Existing bindings are never implicitly resumed or replaced. An explicitly stopped agent requires explicit **Start**. Permissions, unavailable/retired participants and conversation/parent archive restrictions still apply. A broadcast can wake eligible already-running agents according to their policy, but never starts idle agents or resumes stopped ones.

Messages are saved before startup. Startup failure preserves the question for retry without duplicate messages or sessions. Manual activation snapshots and Sends share ordering so a concurrent manual Start cannot skip the first question; Stop and cancellation remain outside that queue. Omitted-target API retries keep a stable inferred payload rather than acquiring a later message's target.

## Reply, threads and remembered panels

The borderless message-actions menu separates **Reply** from **Start thread / Open thread**. Reply changes the recipient without automatically creating a thread. Reply intents are scoped to the initiating person, consumed after handling and canceled across identity changes; another person's recipient and draft remain intact.

Threads begin with the root agent author, or the sole agent recipient of a human root, when unambiguous. Broadcast/multiple/unclear roots infer no agent; an explicit choice overrides the default. Send starts the eligible chosen agent in its separate thread session.

An open thread is remembered per person/channel in the same browser and restored on return or reload without starting an agent. Closing with X or Escape clears that remembered panel. Separate drafts, replies and session state, frozen bounded public context, inherited administration and manual summary transfer are unchanged from v0.0.26. There is no automatic history synchronization or filesystem isolation.

## API compatibility

- Supplied `CreateMessageInput.to` is now authoritative, including `[]`, rather than unioned with body mentions. Omit it for intentional human body-mention resolution. Clients that relied on the former union must adapt; the browser submits its displayed effective targets explicitly.
- Generated agent body text is not a recipient command. Generated replies cannot wake peers, including under `all_messages`. Unaddressed messages no longer implicitly wake the sole agent; API clients should provide their intended targets explicitly.
- The omitted-target local Send fallback is a stable compatibility seed, not evolving server-side sticky state. Sticky API clients must send their effective `to` each time.
- Public API writes remain non-activating. Automatic startup belongs to authenticated `POST /local/conversations/:id/messages` and `LocalControlClient.postConversationMessage()`.

See [Participant targeting](../participant-targeting.md) and [Conversation threads](../conversation-threads.md).

## Compatibility and limitations

- No new database migration is added relative to v0.0.26. Local-control protocol remains **24**; Runtime stays pinned to `86bd35ea846740f55e83038b3ff823d9ddd67e34`, with dependencies and Pi integration configuration unchanged.
- Use Node.js **22.13+** for normal/background-service operation. Foreground use on 22.5–22.12 requires `NODE_OPTIONS=--experimental-sqlite`.
- Back up the complete stopped data directory before upgrading, including both databases, profile and attachments. Do not migrate a running installation manually or downgrade already-migrated data.
- Presets, Copy/message-link actions, cross-device preference synchronization and automatic summary/history transfer are not included.

This release does **not** claim to fix the previously disclosed intermittent native Neon `PendingException` database abort observed in CI on macOS and previously Ubuntu. Its root cause and production impact remain unresolved; green runs do not erase that limitation. No platform coverage or required CI gate is removed. Controlled Runtime tests do not establish arbitrary live-model behavior or abrupt crash-mid-turn durability.

The implementation and fixture continuations have independent Standard-assurance approval. Source-checkout and controlled Runtime evidence do not replace required release-version PR, exact-commit post-merge and tag-workflow checks.

Keep the GitHub release draft until the exact uploaded tarball/checksum/source pins are verified, installed-artifact reopen checks pass in a clean account, and a genuine Pi response is observed. Record that acceptance separately from source-checkout, browser and controlled/fake-Pi checks.
